## 1. 结论先行

### 1.1 总体立场｜理由｜质疑

**立场**｜在组长K确认“GUI 形式不限、4000 行按仓库有效代码总量统计”后，游戏/谜题路线可以成立，但必须从“移植一个游戏”升级为“可复用的谜题规则与验证工作台”。我建议采用**单游戏、模块化单体、纯领域内核 + 静态 Web GUI**，不做多游戏合集，不做后端，不用题库数据凑行数。

**理由**｜

1. 4000 行的可计入范围比原 PM 报告更宽，HTML/CSS/JS/测试可以构成真实总量；但第三方代码和资源不能计入，所以不能把“上游已有 2000 行 + JSON 题库 1500 行”当作安全线。
2. 500 元目标要求“确定性优先”：许可证、来源声明、可运行演示、测试、CI、mooncakes 和申报边界比单纯算法炫技更关键。
3. 谜题的真实扩展应围绕领域能力增长：约束验证、候选边生成、求解器、提示解释、可复现生成、撤销/回放、可访问交互、状态序列化和性质测试，而不是把按钮、颜色和题库条目拆成大量文件。
4. 模块化单体比微服务或复杂前端框架更可逆：一天内可以端到端跑通，之后仍能将 MoonBit 核心发布成库，静态 GUI 只是适配器。

**质疑**｜

- 如果评审把“移植”理解为必须保留上游代码，而不是行为级重实现，则第三方代码不计入的要求会与4000行目标冲突；因此申报材料必须明确“参考上游行为与规则，MoonBit 侧进行独立实现，并新增可复用模块”。
- 4000 行不是官方硬性价值指标。若为了行数牺牲测试质量、模块内聚性或可运行性，反而可能触发“玩具 demo/无价值 wrapper”质疑。
- 16 小时现场冲刺只足以保证一个核心切片；生成器、解释器和完整 GUI 应视为后续增量，不能把全部风险压在第一天。

### 1.2 主选与备选

| 方案 | 决策 | 适用条件 | 主要原因 |
|---|---|---|---|
| **Hashiwokakero 桥接** | **主选** | 采用 `tonivrbic/bridges-solver`（MIT）作为规则/算法参考，独立重写 MoonBit 核心 | 低星、MIT、规则清晰、SVG 记忆点好、算法深度足够，4000 行可由真实模块自然构成 |
| **Kakuro 加数谜** | 备选 A | 接受 Python 上游需要重写，且先准备固定题面作为第一天降级路径 | 低星、MIT、约束求解有深度；但生成器和唯一解验证风险高于桥接 |
| **Nonogram 数织** | 备选 B（交付保底） | 接受上游 54★ 不符合低星偏好，并且明确不复制第三方代码 | 上游最成熟、GUI 最稳、扩展最丰富；但低星偏好和同质化观感明显扣分 |
| **Peg Solitaire 孔明棋** | 条件备选 C | 不使用 `OMerkel/Peg-Solitaire` 的 `Other` 代码，改用 MIT 参考或取得书面许可 | 变体多、演示直观；但上游许可证风险和非矩形棋盘 GUI 风险较大 |
| **Slitherlink 数回** | 条件备选 D | 在无许可证上游不复制代码；最好获得授权或只按公开规则做干净实现 | 视觉效果最强，但 `slitherlink-builder` 无许可证，合规阻断风险最高 |

**最终建议**｜锁定 **Hashiwokakero 桥接**；Kakuro 作为技术备选；Nonogram 作为“最稳但不符合低星偏好”的保底；Peg Solitaire 和 Slitherlink 在许可证问题解决前不进入主实施路径。

## 2. 评估边界与架构原则

### 2.1 计数审计原则

下列代码可计入：

- 独立编写的 MoonBit 领域模型、规则验证、求解器、生成器、提示解释器和序列化逻辑；
- 独立编写的 JavaScript 交互适配器、状态桥接、渲染调度、键盘/触摸输入和动画控制；
- 独立编写的 HTML 结构、CSS 布局/主题/响应式交互；
- 针对规则不变量、求解结果、生成器性质和 UI 状态转换编写的测试。

下列内容不计入：

- 上游仓库直接复制、逐行翻译或机械改名后的代码；
- 编译生成的 WASM、绑定文件、类型声明、打包输出；
- 题库、关卡 JSON、图片、音效、字体和其他资源；
- 自动生成的代码、代码生成器的输出文件、依赖包源码和第三方库代码；
- 只为增加行数而拆分的薄包装、重复 DTO、无业务含义的常量表。

**建议审计方式**｜仓库内增加一份人工维护的 `CODE-SCOPE.md` 或 README 计数说明，按“自有源码 / 测试 / 资源 / 生成产物 / 第三方”列出统计边界。该说明本身不依赖于行数，目的是防止复审时无法解释代码来源。

### 2.2 推荐架构

```text
                 ┌─────────────────────────────┐
                 │ 静态 Web 入口                │
                 │ HTML + CSS + 少量 JS         │
                 └──────────────┬──────────────┘
                                │ 事件/视图模型
                 ┌──────────────▼──────────────┐
                 │ Web 适配器层                 │
                 │ DOM/SVG 渲染、Pointer Events │
                 │ WASM 桥接、动画、持久化       │
                 └──────────────┬──────────────┘
                                │ 纯数据命令/快照
                 ┌──────────────▼──────────────┐
                 │ MoonBit 应用层               │
                 │ 游戏会话、关卡、提示、回放    │
                 └──────────────┬──────────────┘
                                │
                 ┌──────────────▼──────────────┐
                 │ MoonBit 领域层               │
                 │ 规则、不变量、求解、生成      │
                 └──────────────┬──────────────┘
                                │
                 ┌──────────────▼──────────────┐
                 │ 测试与性质验证               │
                 │ 单元测试、回归题、随机性质    │
                 └─────────────────────────────┘
```

**架构选择**：模块化单体，而不是微服务或事件总线。事件只在进程内作为命令/状态转换使用，不引入网络分布式复杂度。

**依赖方向**：UI → Web 适配器 → 应用接口 → 领域内核；领域内核不引用 DOM、浏览器 API、WASM 运行时或具体存储实现。

**可逆性**：

- DOM 与 SVG 可替换为 Canvas，不影响规则内核；
- localStorage 可替换为服务端存储，不改变领域模型；
- 单个谜题可在后续抽出为 mooncakes 包，但第一天不提前拆包；
- 求解器与 GUI 通过不可变快照交互，便于后续 CLI、Web Worker 或原生宿主复用。

### 2.3 不做的事情

- 不做账号、排行榜、联网对战和后端数据库；
- 不做多个谜题拼盘来掩盖单个领域不足；
- 不把大量关卡数据算入代码量；
- 不把上游原始代码直接复制后宣称为本人成果；
- 不在第一天引入 React、复杂状态管理、服务端渲染或微服务；
- 不把许可证未确认的仓库作为可复制代码来源。

## 4. Top5 详细评估与代码量构成

> 下面的“核心移植”均指：根据上游可验证行为/规则进行**独立 MoonBit 重实现和接口适配**。第三方原始代码和机械翻译代码按 0 行计入。以下为可审计的目标预算，不是已完成代码量。

### 4.1 Top1：Hashiwokakero 桥接

#### 立场｜理由｜质疑

**立场**｜**主选**。这是低星、许可证、一天可玩和复审算法深度之间最平衡的候选。

**理由**｜

- `tonivrbic/bridges-solver`：7★、MIT、TypeScript，语言和规则结构便于理解；
- 规则可以在演示中快速说明：岛屿数字约束、桥最多两条、桥不能交叉、全部岛连通；
- SVG 对“岛—桥—连通区域”表达自然，GUI 不需要复杂坐标系统；
- 领域边界清楚：候选边、局部数字约束、全局连通性和唯一解验证；
- 4000 行可以由规则内核、求解/提示、生成器、回放、SVG/交互和测试构成，不依赖题库数据。

**质疑**｜

- 桥的点击热区和“桥数量循环”比 Nonogram 更容易产生误触；必须提供键盘方向操作或明显的悬停预览。
- 生成器和唯一解验证若放进第一天主路径，可能挤压基础 GUI；第一天应允许固定题面运行，生成器作为第二切片。
- 仅有 BFS 连通性不够形成复审亮点，需要加入约束传播、候选边消除和解释性提示，否则会被看作普通小游戏。

## 5. 演进计划与切换策略

### 5.1 实施阶段

| 阶段 | 目标 | 通过门槛 |
|---|---|---|
| S0 许可证/查重确认 | 确认主选 MIT、无 MoonBit 同题实现、来源边界 | 未通过则不开始移植 |
| S1 核心垂直切片 | 固定题面 + 一个页面 + 可走一步 + 胜负判定 | 评审可在浏览器完成一局 |
| S2 领域加深 | 求解器、提示、错误诊断、撤销/回放 | 不再是只能手玩的 wrapper |
| S3 代码量与质量 | 生成器、序列化、性质测试、主题/可访问性 | 4000 行审计预算、测试全绿 |
| S4 合规交付 | CI、README、许可证、来源、mooncakes、演示 | 复审清单全绿 |

### 5.2 Go/No-Go 切换点

- **T+1h**：MoonBit WASM/静态页面无法冒烟 → 不继续加功能，先解决工具链；
- **T+4h**：桥接核心不能可靠走一步并判定非法 → 切 Kakuro 固定题面或 Nonogram 基础切片；
- **T+8h**：核心和基础 GUI 已可玩但生成器未完成 → 冻结生成器，优先测试、提示和回放；
- **T+12h**：有效代码预算仍低于 3200 → 加入真实的解释器、状态编解码和性质测试，不添加空壳页面；
- **T+14h**：测试不全绿 → 冻结新功能，只修核心和回归测试；
- **T+15h**：许可证/来源/README 未完成 → 放弃非必要视觉功能，优先合规。

### 5.3 为什么不采用“两个游戏合集”

合集看似容易达到4000行，实际会带来两个领域内核、两套 UI 状态和两套回归矩阵，扩大测试面并降低申报边界清晰度。对500元目标，单个游戏的深度模块比两个浅层游戏更容易证明“实质新增”和“本人贡献”。

## 6. 主选 Hashiwokakero 的领域设计

### 6.1 限界上下文

| 上下文 | 职责 | 不负责什么 |
|---|---|---|
| Puzzle Domain | 岛屿、候选边、桥数、连通性、完成判定 | DOM、存储、网络 |
| Solver & Explanation | 约束传播、候选消除、搜索、提示原因 | 页面布局、题库资源 |
| Session | 当前局、撤销/重做、回放、计时状态 | 规则本身的正确性 |
| Web Presentation | SVG/HTML/CSS、指针/键盘/触控、动画 | 直接修改领域内部状态 |
| Verification | 单测、性质测试、回归题面 | 生产运行时逻辑 |

### 6.2 聚合与不变量

**聚合根**：`PuzzleSession`。所有用户命令经过聚合根产生新快照，UI 不可直接修改岛屿数组。

**关键不变量**：

1. 桥只能连接同一行或同一列中无遮挡的相邻岛屿；
2. 同一对岛屿的桥数只能为 0、1、2；
3. 桥不能与其他桥交叉；
4. 任一岛屿当前桥数不超过题面数字；
5. 完成状态要求所有岛数字恰好满足，并且全图连通；
6. 回放每一步都必须可重放、可撤销，非法命令不污染历史；
7. 生成器输出的题面必须可解析，若宣称唯一解则必须经过独立解数验证。

### 6.3 应用接口边界

- 输入：`StartPuzzle`、`ToggleBridge`、`RequestHint`、`Undo`、`Redo`、`ReplayToStep`；
- 输出：只读 `BoardView`，包含岛、桥、候选动作、错误诊断和完成状态；
- JS 只负责将 Pointer Event 映射到领域命令，不在 JS 端重复实现规则；
- 任何可复用算法都优先放在 MoonBit，HTML/CSS/JS 负责表现和宿主适配。

## 7. 交付后的实际实现边界

当前发布快照实现的是固定题面 + 纯 MoonBit 规则内核 + 静态 Web GUI 的可运行垂直切片。生成器、完整搜索求解器与唯一解验证属于评估文档中的后续演进方向，不应被描述为当前版本已实现功能。

当前代码已提供：

- 岛屿、桥、棋盘、游戏会话及不可变快照；
- 桥数量、遮挡、交叉、度数、连通性与完成判定；
- 撤销/重做与基于局部约束的确定性提示；
- 快照序列化/反序列化；
- 浏览器静态 Demo、键盘操作、关卡切换与本地状态持久化；
- MoonBit 黑盒/白盒测试及 JS 导出接口。

## 8. 架构决策记录摘要

### ADR-ARCH-001：采用单游戏模块化单体

**状态**｜提议

**背景**｜需要在有限时间内完成可运行 GUI，并达到含前端与测试的4000行有效代码，同时保持复审可解释性。

**决策**｜使用 MoonBit 纯领域内核 + 应用会话层 + 静态 HTML/CSS/JS 适配器；第一阶段不拆微服务、不引入后端。

**备选方案**｜

1. 多游戏合集：行数增长快，但领域边界和测试复杂度翻倍，容易像拼盘。
2. 微服务/前后端分离：可扩展性更强，但本项目没有并发、部署自治或团队协作需求，属于架构过度。
3. Canvas 游戏框架：动画控制集中，但无障碍和 DOM 调试较差；先用 SVG/DOM，必要时再替换渲染器。

**影响**｜核心规则易测、可发布为 MoonBit 库，静态页面可直接演示；代价是 JS 适配器需要维护状态同步，不能在浏览器端复制一份规则逻辑。

### ADR-ARCH-002：以 Hashiwokakero 为主选

**状态**｜提议

**背景**｜需要同时满足低星偏好、来源合规、一天可玩、真实扩展和复审算法抗辩。

**决策**｜优先选择 7★、MIT、规则清晰且 SVG 友好的桥接；将 Kakuro 作为约束求解备选，将 Nonogram 作为交付保底但显式标注54★。

**备选方案**｜Nonogram 工程最稳但星数高；Slitherlink 视觉最强但无许可证；Peg Solitaire 变体强但 Other 许可证有风险。

**影响**｜牺牲了 Nonogram 的成熟上游和更强视觉揭晓效果，换取低星匹配度和更好的独立贡献叙事；生成器和 SVG 交互是主要风险。

## 9. 关键风险台账

| 风险 | 等级 | 触发信号 | 应对 |
|---|---|---|---|
| 主选上游许可证或来源描述不完整 | 高 | MIT 文件无法在快照中确认 | 暂停复制；只做独立规则实现并核验，必要时切 Kakuro |
| 第三方代码被误计入4000行 | 高 | 计数表含上游翻译/绑定/资源 | 建立自有源码清单，排除原始/生成/资源文件 |

| GUI 与 MoonBit 状态不同步 | 中 | 点击后视图与领域快照不一致 | 单向命令 + 不可变快照；JS 不保存第二份规则状态 |
| 被判玩具 demo | 高 | 只有可玩棋盘，没有求解/解释/测试 | 优先加入约束传播、提示原因、回放和性质测试 |

| 测试占比过高但领域功能不足 | 中 | 代码量主要来自重复测试夹具 | 测试覆盖不变量和性质；不复制大段 fixture 数据 |
